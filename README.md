推定原因は「NVM読み出しの返りペイロードが“各ワードごとに [DATA(2B), STATUS(2B)] の4バイト”で並ぶ」のに対し、抽出位置を誤っていたことです。加えて、先頭ヘッダは2バイトではなく4バイト捨てる必要があります。

観測結果の読み解き
- 2つ目の修正（ダミー=2B/ワード、resp[4:]から連続データとみなす）の結果が
  E2 83 | 80 00 | 38 06 | 00 00 | 20 00 | 00 00
  となっています。これは「DATA1, STATUS2, DATA3, STATUS4, DATA5, STATUS6」という交互パターンを示しており、デバイスがワードごとにデータ2バイト＋ステータス2バイトを返していることを強く示唆します。ダミーを2B/ワードしか送っていないため、偶数番目のデータ（D2, D4, D6）が取り切れていません。
- 1つ目の修正（ダミー=4B/ワード）では、各4バイトブロックの“後ろ2バイト（STATUS）”を抜いてしまったため、先頭が 80 00（ステータス）で埋まる結果になりました。

結論
- 先頭4バイトのヘッダを捨てた後、各ワードは「4バイト単位」で返り、その先頭2バイトがデータ、後ろ2バイトがステータスです。
- よってダミーバイトは 4*word_len だけ送り、各4バイトブロックの「先頭2バイト」を連結して返すのが正解です。

修正コード例（read_nvm1）
```
def read_nvm1(self, addr_msb, addr_lsb, word_len):
    # 先頭4バイト: コマンド/アドレス/ダミー
    # 以降、各ワードは [DATA(2B), STATUS(2B)] の4バイトで返る前提
    tx = [READ_NVM1 | addr_msb, addr_lsb, 0x00, 0x00] + [0x00] * (word_len * 4)
    resp = self.spi.xfer2(tx)

    if len(resp) < 4 + word_len * 4:
        raise IOError(f"SPI response too short: {len(resp)} bytes")

    payload = resp[4:]  # ヘッダ4バイトを捨てる

    data_bytes = []
    for i in range(word_len):
        base = i * 4
        # 各4バイトブロックの先頭2バイトがデータ（ビッグエンディアン想定）
        data_bytes.extend(payload[base : base + 2])

    return bytearray(data_bytes).hex().upper()
```

この修正で、提示のTID期待値
E28338062000000001C74D68
に一致するはずです（6ワード=12バイト）。

補足
- これで「ダミー=4B/ワード」「ヘッダ4B削除」「各ブロック先頭2Bがデータ」という実デバイスの振る舞いに合致します。
- 万一、データのエンディアンが逆（[低,高]）であれば、extendする2バイトの順を反転してください。通常は上記で正しいはずです。
- 既存の read_model_number / read_nvm_user_memory もこの read_nvm1 を経由して正しく読めるようになります。
